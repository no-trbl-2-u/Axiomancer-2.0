# AI Instructions: Axiomancer-2.0 Project Overview

## Project Purpose
Axiomancer-2.0 is a philosophical role-playing game where players engage with logic and logical fallacies as a combat and progression system. The game combines traditional RPG mechanics with philosophical concepts, creating a unique narrative-driven experience.

## High-Level Architecture

### Monorepo Structure
```
/workspace/
├── axiomancer-backend/      # Node.js/Express REST API
├── axiomancer-frontend/     # React/TypeScript SPA
├── axiomancer-documentation/ # Game design docs
├── docker-compose.yml       # Container orchestration
└── [various .md files]      # Project documentation
```

### Technology Stack

#### Backend
- **Runtime**: Node.js with Express
- **Language**: TypeScript
- **Database**: SQLite (local), PostgreSQL (staging/production)
- **Authentication**: JWT (jsonwebtoken)
- **Security**: bcryptjs for password hashing
- **API Style**: RESTful

#### Frontend
- **Framework**: React 18
- **Language**: TypeScript
- **Styling**: @emotion/styled (CSS-in-JS)
- **State Management**: Zustand (with persist middleware)
- **Routing**: React Router v6
- **HTTP Client**: Axios
- **Build Tool**: Vite

#### DevOps
- **Containerization**: Docker + Docker Compose
- **Database**: PostgreSQL 16 (Alpine)
- **Web Server**: Nginx (for frontend static files)
- **Environments**: Local, Staging, Production

## Core Game Concepts

### 1. Philosophical Combat System
- Combat revolves around **logical fallacies** (see `axiomancer-documentation/rules/all-fallacies-reference.md`)
- Players learn and master different fallacies as "skills" or "attacks"
- Three philosophical aspects: Physical, Mind, Ailment

### 2. Character System
- **Stats**: Divided into Physical, Mind, and Ailment categories
- **Portraits**: Gender-based character portraits (male/female)
- **Progression**: Experience-based leveling with stat point allocation
- **Equipment**: Slot-based equipment system
- **Skills**: Fallacy-based abilities tied to philosophical aspects

### 3. Game Structure
- **Node-based exploration**: Navigate through location nodes on maps
- **Events**: Combat, dialogue, story progression
- **Quest system**: Track player objectives
- **Inventory**: Item collection and management

## Data Flow

### Authentication Flow
```
User → LoginPage → authStore → Backend API → JWT Token → localStorage
                                     ↓
                              Database (users table)
```

### Character Persistence Flow
```
Game Action → gameStore → characterService → Backend API → Database
     ↓                                                          ↓
Auto-save (500ms debounce)                        character_states table
```

### Combat Flow
```
Player Action → CombatModal → gameStore.updateCombat() → Enemy AI Response
     ↓                                  ↓
Combat State Updates              Save to Database
```

## Key Design Patterns

### 1. Store-Based State Management (Zustand)
- `authStore`: User authentication state (with localStorage persist)
- `gameStore`: All game mechanics (character, location, combat, inventory)
- Stores are UI-agnostic; components consume and display state

### 2. Service Layer Pattern
- `characterService`: HTTP calls for character persistence
- `database.service`: Database abstraction (SQLite/PostgreSQL)
- `auth.service`: User authentication logic

### 3. Route Protection
- Protected routes require authentication
- Middleware: `authenticateToken` validates JWT on backend
- Frontend: `ProtectedRoute` component wraps authenticated pages

### 4. Component Organization
```
components/
├── game/        # Game-specific UI (combat, character screens, events)
├── shared/      # Reusable UI components (buttons, modals, tooltips)
└── figma/       # Design system components
```

## Database Schema

### Key Tables
1. **users**: User accounts (id, email, password_hash, firstName, lastName)
2. **character_states**: Serialized game state per user (JSON columns for flexibility)

### Character State Structure
- character_data (JSON): Full character object
- story_data (JSON): Story progression flags
- inventory_data (JSON): Items and equipment
- locations_data (JSON): Unlocked locations and nodes
- quest_log_data (JSON): Active and completed quests

## Developer Experience Standards

1. **Linting**: ESLint configured for TypeScript
   - Backend: `npm run lint` / `npm run lint:fix`
   - Frontend: `npm run lint` / `npm run lint:fix`

2. **Formatting**: Prettier
   - Backend: `npm run format` / `npm run format:check`
   - Frontend: `npm run format` / `npm run format:check`

3. **Type Safety**: "Very Explicit types with Typescript" (project mandate)
   - Always prefer explicit types over `any`
   - Define interfaces for all data structures
   - Use strict TypeScript configuration

4. **Testing**: Playwright for end-to-end testing
   - Frontend: `npm run test` (runs Playwright tests)
   - Test file: `/workspace/axiomancer-frontend/playwright-test.js`

## Architectural Principles

1. **Separation of Concerns**: UI components should be thin; business logic lives in stores
2. **Type Safety First**: Always define types before implementation
3. **RESTful API Design**: Backend follows REST conventions
4. **Stateless Backend**: All state persisted in database; JWT for auth
5. **Component Reusability**: Build shared components in `components/shared/`
6. **Mobile-First Responsive**: Design for mobile, enhance for desktop

## Common Gotchas

1. **Auth Token Retrieval**: Frontend manually parses localStorage for auth token (see `characterService.ts`)
2. **Auto-Save Debouncing**: Game saves are debounced by 500ms; closing browser too quickly may lose data
3. **Type Mismatches**: ApiError type differs between frontend/backend (see `shared-types.md`)
4. **Character ID Generation**: Uses `Date.now().toString()` which could cause collisions
5. **Two Combat Systems**: Both "old" and "new" combat types exist (see `Types-Issue.md`)
6. **No Zustand Persist for gameStore**: Game state relies entirely on backend saves, no localStorage fallback
